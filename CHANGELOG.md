# Changelog

## 0.3.2

### Changed
- **Console channel: Resolve stays in the background.** Until now every call brought Resolve to the front, typed, and gave the front back: two app switches and about 1.5 s per call, during which the user could not use the machine. A call now leaves Resolve where it is. Measured on Resolve 21.2.0 Free with another app in front: 30 calls with a median of 0.026 s each (the first, which types the helper, 0.44 s), a 6,000-row answer in 0.17 s, and the app in front never changed.
  - Why it needed the front before: System Events finds a window in the app's window list, and that list leaves out the Console while Resolve is in the background (the Console is a panel that hides then). Accessibility itself still hands the Console out as Resolve's focused window, an input or output found once keeps answering while its window is hidden, and a Return sent to Resolve's process runs the line. The server now talks to Accessibility directly (no new dependency) and keeps those parts.
  - If the user last clicked somewhere else in Resolve, the Console is given the keyboard focus inside Resolve first; that changes nothing on screen while Resolve is in the background.
  - Resolve still comes to the front when the Console cannot be reached that way: it is closed, a dialog in Resolve has the keyboard, or a Return sent to the process did not arrive (the line is then typed again the old way; after two in a row the old way is used from then on). `RESOLVE_PILOT_CONSOLE=front` asks for the old way always.
  - Measured with Resolve on another desktop than the app in front. Not tried: Resolve visible behind another app's window on the same desktop.
- Console channel, when Resolve does have to come forward: a run of such calls switches apps once. Resolve stays in front for 4 seconds after a call (`RESOLVE_PILOT_CONSOLE_HOLD`, 0 gives the front back after every call, at most 60) while the next call would need it there again; a call in that time starts at once, and the app that was in front comes back after the last one. Measured: back to back 1.5 s before, 0.82 s so. A user who went to a third app meanwhile is left there, the front is not given back under a call that is running or while another resolve-pilot session types, and a server that exits gives it back first. As soon as the next call can be made in the background, the front is given back at once instead.
- The package starts under its own name too (`davinci-resolve-mcp-free`, next to `resolve-pilot`), and carries what PyPI and the MCP Registry need (`server.json`, a publish workflow that stores no token).

### Fixed
- Console channel: Return can no longer land in another app. It used to be pressed through System Events, which gives a key to whichever app is in front at that instant; the front and the focus were checked just before, but an app taking the front in between would have received the Return. The key event now goes to Resolve's process id with no modifier keys. System Events presses it only where such a key cannot be sent.
- Console channel: a line that was typed but not run is noticed. Seen once on 21.2.0 Free with the user at the keyboard: the request's line never appeared in the Console, and the call waited 30 seconds for "did not answer in time", which reads as if the code might have run. The Console empties its input before it runs a line, so a line still there (three looks in a row, 0.6 s after Return) has not run: it is typed again, once, and if Return still does not arrive the call ends within seconds, says that nothing ran, and takes the line out of the input. Measured with a Return that was deliberately not sent: answered in 2.3 s, run exactly once.
- Console channel: a Resolve that is busy (a long import, the request before still running) is said so after ten seconds, with nothing typed, instead of after a 30-second wait in front.

## 0.3.1

### Fixed
- Console channel: a request could end with "Can't get text area 1 of window 1" before anything was typed. System Events numbers Resolve's windows by their place in the stack, and the number found for the Console meant another window a moment later (raising the Console renumbers them; so does any window that comes or goes). Seen once on Resolve 21.2.0 Free, on the third call of a fresh server. The Console is now looked up again after it is raised.
- Console channel: of two requests sent back to back, the second often failed ("did not come to the front", "Console window could not be opened") when another app was in front. The first request hands the front back to that app; its activation could land after the second request had brought Resolve forward, and Resolve's windows were gone again. Handing the front back now waits until that app is in front, and a typing attempt that loses its footing starts over (Resolve forward again, in front for three looks in a row, Console found, typed), up to six times. Return is still the last step, so nothing is typed twice. When Resolve cannot be kept in front at all (the user working in another app at that moment), the request ends within about ten seconds and says so. Measured with a real MCP client and the Claude app in front: before, 5 of 6 back-to-back frame requests failed; after, 21 of 21 calls went through, and 40 of 40 requests with page changes in between.

## 0.3.0

Focus: one request, a finished rough cut. The agent can *look* — at footage, and at Resolve itself — find problem stretches, cut talking footage by the word, preview and check the cut without Resolve, and control Resolve Free 21.2 again (macOS).

Verified live on Resolve 20.3 (Free, macOS): screenshot_resolve, grab_frames, scene_frames, read_video, analyze_quality and add_quality_markers (including re-runs replacing only their own markers).

### Added
- **Resolve Free 21.1.2+ is live again on macOS: the `console` channel.** The bridge cannot exist there (no script starts from the menu, Console Lua cannot reach files), and nothing is done to get that access back. What every Free user still has is the Console: type Lua, read what it prints. The server now does that for the user through macOS Accessibility: it puts a tool's Lua into the Console's input, presses Return and reads the output text. No file inside Resolve, no clipboard, no screenshot.
  - `channel="auto"` picks it after the bridge and before `manual`, and only where the bridge cannot run; `channel="console"` asks for it anywhere on macOS. `resolve_pilot_status` reports `channel: "console"` and, when it is not usable, what is missing (the app to allow under Accessibility). `setup_bridge(action="start")` there starts Resolve and waits until the Console answers (`console_ready`). `run_lua` uses it too. `RESOLVE_PILOT_CONSOLE=off` turns it off.
  - Return is pressed only while Resolve is the front app and the Console's input has the keyboard focus; otherwise nothing is typed and the tool says why. The app that was in front gets its place back after every call. Reading `resolve://state` never touches the Console.
  - Measured on 21.2.0 Free before building: the Console keeps its last 131,072 characters and loses a longer line whole, so answers travel as plain ASCII in parts of 60,000 with their length; globals survive between entries, so the helper (the bridge script in a mode that loops over nothing and opens no file) is typed once per Resolve session; Resolve's windows are visible to Accessibility only while it is in front; after a page change the Console's input takes the focus only once its window is raised.
  - Run for real on 21.2.0 Free: the 198-clip cut imported and checked against its plan (198 of 198, 22 s), state with all clips read back (1 s), the built-in LUT on 198 clips, markers, 176 captions, a checkpoint, frames rendered by Resolve from four pages. Then every other Resolve tool on a small timeline: media import, a timeline from source ranges, clip colour, zoom and opacity, tracks, a title, a grade, marker edits, quality markers, FCPXML and EDL export, a 9:16 copy, ripple delete, checkpoint restore, a project backup, a rendered MP4, creating and reopening projects; and the server driven by a real MCP client over stdio. A first call takes 1.3 s, later ones about 0.7 s, a 370 KB answer 3.8 s in seven parts.
  - Not covered: Windows and Linux (no way to type for the user there; `manual` remains), a Resolve in another language than English when the Console window is closed (the menu entry is looked up by its English name), and 20.x, where the Console has language tabs and the bridge is the better way anyway.
- `timeline_frames` says when two positions came back as the very same picture (`same_picture`): right for a still stretch, otherwise a frame Resolve had not drawn yet. Seen once on 21.2.0 Free, not reproduced in 27 further stills.
- **Word-level cuts for talking footage.** `transcribe_audio` now records every word's time by default (`word_timestamps=true` used to return nothing: the words were never stored) and `detail="words"` shows them with `segment.word` addresses and pause marks. `plan_from_transcript` takes `drop_words` (`"12.3"`, `"12.3-5"`) to cut fillers, repeats and false starts out of the lines it keeps, and `max_pause_seconds` to tighten long pauses inside them. Every cut is placed where the voice actually dips between two words, found in the audio's voice-band level curve (stored with the transcript): Whisper's word edges were measured to be up to ~0.5 s off around pauses (a word that really ended at 1.62 s was reported to end at 1.30 s), so cutting on them clips words. A valley that is wide and deep enough relative to the words around it is a pause and the cut keeps `pad_seconds` of it; in continuous speech the cut goes to the quietest point and is reported as `tight`; sound between far-apart words (music, waves, laughter) is left out. `cut_report` counts both kinds, and says so when the audio could not be measured. A segment in which nothing is said is not made into a clip (Whisper closed a real vlog file with an empty 17 ms segment, which became a clip of less than a frame and a plan error); `cut_report.empty_segments_skipped` lists them. A fixed silence threshold was tried first and dropped: on handheld vlog footage it found no pause at all, because the gaps between words there are only 8-12 dB below the words. Measured on 17 minutes of real vlog footage (10 clips, 1,221 words, cleaned cuts): cut points that land in sound went from 31% (Whisper's times) to 10%, and words lost or changed when the cut audio is transcribed again from 28.0% to 25.1%. That second number is a noisy measure and says the cuts are better, not that they are word-perfect.
- `scan_speech` lists `likely_invented`: segments that read like the subtitle credits and sign-offs Whisper writes over music, noise or silence ("Altyazı M.K.", "Thanks for watching", "Subtitles by…"). In 11 real vlog transcripts 6 of 350 segments were such lines, in 4 files; they had word probabilities of 0.87-0.94 and sound under them, so only the wording gives them away. A speaker can really say it: candidates, like the rest of the scan.
- **One request, a folder of clips.** `scan_folder(folder)` lists a shoot's media files in recording order (the camera's own time when every file has one, else the files' times) with length, frame, rotation tag and sound, and with `transcribe=true` starts every transcript in the background (`status: running` per file, call again; one failing file does not hide the others). A client with only MCP tools could not list a folder at all. `plan_from_transcript(append_to=plan_id)` adds the next file's cleaned cut to the same plan, which remembers every source's transcript, so captions and the preview cover the whole cut. `edit_plan` has a `turn` operation for a source that plays on its side (90 / 180 / 270° clockwise): `render_preview` shows it, and `export_fcpxml` writes it into the file (see "Tried in Resolve" below). New guide `resolve-one-prompt-edit`: the whole run from the folder to the preview the user watches. Run on a real shoot through the tools only: 11 files (13 min 7 s) scanned and transcribed, 10 cut into one plan of 201 clips and 6 min 23 s with the mechanical choices (hesitations, repeats and earlier retakes out, pauses over 0.5 s shortened), six sideways sources turned after looking at one frame each (one direction was wrong at first and showed in the next render), preview with 177 captions rendered frame-exact in 3 to 7 minutes (three runs: 184 s, 331 s, 400 s). The check listed 10 cuts in sound, 19 level jumps, 5 flash clips and 6 fast captions; they were not worked through, and nobody has watched the result yet.
- **What was done by hand around the tools is now in the tools.** In the Resolve trial four steps needed a shell, another app's AppleScript, raw Lua and a scratch script; a client with only the MCP tools could not have done them.
  - `import_timeline(plan_id=...)` reads the timeline back and compares it with the plan: the clip count, every clip's start and end frame, its source file and in-point (one frame of tolerance for a conformed source) and the turns. `plan_check.ok` is true only when all of it matches; otherwise `positions_off` / `sources_off` / `turns_off` / `frame_rate` list what differs (ten each, with the full count). On the real 198-clip cut in Resolve 20.3 Free: the file from `export_fcpxml` passes 198 of 198; the earlier file with the phone's average frame rate comes back with 57 positions and 135 turns off. Without a live channel the result says the check was not made.
  - `manage_projects` (new tool): the projects in Resolve's current project folder and the open one; `open` and `create` save the open project first and refuse to leave it when that save fails while it has timelines; a wrong or taken name returns the names there are. A created project is saved at once, because Resolve lists it only then (seen on 20.3). Tried in Resolve 20.3 Free: a scratch project created, the test project opened again with its current timeline.
  - `setup_bridge(action="start")`: starts Resolve when it is closed, clicks Workspace > Scripts > ResolvePilotBridge (macOS, when the server has Accessibility permission; retried while Resolve is still loading, not retried without permission) and waits for the bridge's heartbeat. `left_for_user` says exactly what remains when a step could not be done, and a Resolve where the bridge is known not to start is not clicked. Run for real with the bridge already running and from a closed Resolve (it started Resolve 21.2); the menu click itself is covered only by tests with a simulated machine.
- **Phone HDR clips no longer look pale: a built-in conversion.** An iPhone records HLG with BT.2020 colour; a Resolve project without colour management shows those numbers as Rec.709, bright, flat and grey. `probe_media` and `scan_folder` now say `hdr` (`hlg` / `pq`), `export_fcpxml` returns `hdr_sources` and names the next step, and `apply_lut(lut_path="hlg-to-rec709")` puts a built-in LUT on exactly the clips Resolve itself tags Rec.2100 HLG (`skipped` counts the others; an all-SDR timeline is left alone and the result says so). The LUT undoes the HLG curve, converts the colours to BT.709 and encodes with two fitted numbers (power 0.40, saturation 1.14); it is generated in code, no file ships. Fitted to Apple's own SDR conversion of the same files (`avconvert`) on five frames of three clips and checked on three others, then measured in Resolve 20.3 Free on all eight (PSNR against Apple's frame): 17-20 dB untouched, 37-41 dB with the LUT; brightness within 0.007 and colour within 5% of Apple's. Also tried and worse: Resolve's own colour management with DaVinci tone mapping (13-14 dB, brighter still) and a single CDL (29-30 dB). `render_preview` shows HLG sources through the same LUT, after the downscale (a 4K frame through the LUT took 3.6 times as long), and tags the file Rec.709: on the real vlog preview the same eight frames come to 34-37 dB (one frame also decoded by Apple's own decoder: 36.5 dB), rendered frame-exact in 6 min 9 s, inside the range of the runs before. Without `lut3d` in ffmpeg the result says so in `not_shown`. Stored previews are rendered again once. HDR10 (PQ) is recognised but not converted, and the tools say so. New guide `resolve-phone-hdr`. Measured on daylight clips from one iPhone 14 Pro; night footage and other phones are not tried.
- **Tried in Resolve: the one-request cut on a real timeline, and turns that travel in the file.** The vlog cut (198 clips from 10 phone clips, 6 min 20 s) was exported, imported into Resolve 20.3 Free and read back: every clip starts and ends on the plan's frame and plays the plan's source range, and the plan's captions (`add_subtitles`) landed 176 of 176, none more than a frame from the file. `export_fcpxml` now writes a plan's `turn`s as `<adjust-transform>`: Resolve reads the rotation and scale into each clip's Rotation Angle and Zoom (135 of 135 clips, read back; a 90°, a 180° and a 270° turn, with dissolves, with a music bed on the turned first clip, with and without a fade-in), so sideways shots arrive upright and filling the frame, with no step after the import. The zoom is worked out from the picture as its file is tagged and the timeline's size, for a project that fits mismatched clips into the frame (Resolve's default). Looked at one frame of each of the 10 sources in Resolve; nobody has watched the timeline play. `timeline_frames` shows the picture but not the captions.
- **A preview without Resolve, checked automatically: `render_preview(plan_id)`.** Renders a plan to a small MP4 with ffmpeg alone (a background job: `status: running`, call again; one file per plan, re-rendered only when the plan, its captions or a source changed). Every clip gets exactly the frames `export_fcpxml` gives it and its audio is cut on the matching sample, so the preview's times are timeline times: `grab_frames` / `read_video` on the preview look at the cut, and the plan's captions ride along as a subtitle track. A render that does not have exactly the plan's frames is not written. Fade gaps are black, the audio bed is mixed in, a source that ends early holds its last frame; dissolves play as cuts and the result says so (`not_shown`). The result lists `issues`, each with its clip and timeline second: `cut_in_sound` (the sound does not dip at the cut: a clipped syllable or a click is likely), `level_jump` (the voice level steps 8 dB or more across a cut), `flash_clip` (under 0.4 s), `silence` / `black_picture` / `frozen_picture` (from `analyze_quality` on the preview, fade gaps excepted), `fast_caption` (over 25 characters a second) and `rotated_source` (a quarter-turn tag: look whether it is right). They are candidates to look at, not verdicts. On the real vlog footage (10 cuts, 310 clips, 116 real cuts, 9 min 13 s of preview from 4K HEVC rendered in 3 min 19 s, every one frame-exact) it listed 16 cuts in sound, 30 level jumps (checked on one clip: a speaker far from the phone followed by the one holding it, 14 dB apart), 11 flash clips and 7 captions too fast; nobody has listened to the 16 cuts yet. Not shown burned in: this ffmpeg build has neither the `subtitles` nor the `drawtext` filter, so captions are a track to switch on in the player.
- `probe_media` reports `rotation`: the degrees a phone tagged the picture to be turned for display (`width` / `height` stay the stored ones). 8 of the 10 real vlog clips are tagged 90°; on the one looked at the picture is upright as stored, so players show it on its side; `render_preview` shows them as players do and lists `rotated_source`. Resolve 20.3 shows them the same way (on their side).
- The tool list takes less room: an optional parameter is advertised as its type instead of `anyOf [type, null]` with `default: null` (the advertised schemas went from 49,895 to 45,863 characters before `render_preview` was added; some clients also lost the type behind the `anyOf`). Null is still accepted. Nested models keep theirs, where null can mean something (`audio_bed: null`).
- **Captions that follow the cut.** `export_srt(plan_id=...)` and `add_subtitles(plan_id=...)` time the captions to a plan's timeline instead of the source file: each clip takes the transcript words spoken inside its source range and puts them where the clip plays, so kept segments, a new order, dropped words, trims and fades are all followed, on the same frame positions `export_fcpxml` writes. Until now captions only fitted a timeline that played the transcribed file from its start, and a rough cut had to be rendered and transcribed again. A plan from `plan_from_transcript` remembers its transcript; other plans take `transcript_ids`. Clips whose source has no transcript are reported (`clips_without_transcript`), a transcript that is no longer stored or has no word timings is a warning, and a plan where nothing can be captioned is an error. Words become cues by reading rules: a new cue when two lines are full, after a sentence, at a pause once a line is full (for speech Whisper left unpunctuated), after 6 s and after a silence; a caption that is short for its text is held (17 characters a second, at least 0.7 s) when nothing follows, and cues never overlap. Measured on the same real vlog footage (9 clips cut into 311 pieces, 1,217 caption words; the cut audio was rendered and transcribed again, 940 words could be paired): 93% of the caption words are within 0.3 s of where the word is heard in the cut and 96% within 0.5 s (median per clip 0.01-0.03 s); at the source's own times, which is what the captions had before, 5% are. Not yet tried on a timeline in Resolve: only the caption file is new, putting it on the subtitle track is unchanged.
- `scan_speech`: the candidates an editor looks for in a transcript — long pauses, filler words (hesitation sounds, and discourse words such as "like" / "şey" marked as such), immediate repeats and retakes — each with the `drop_words` value or segment index that removes it. Candidates, not decisions.
- `manage_timelines` (list with duration / fps / size / current, open, rename, duplicate without leaving the current timeline) and `edit_markers` (list, delete by frames / seconds / color / customData prefix — never everything at once — and update name / note / color in place). Verified live on Resolve 20.3 Free.
- `make_format_version`: copy the current timeline at 9:16 (Shorts / Reels / TikTok), 4:5, 1:1 or a custom size, clips centre-cropped to fill (or fitted), and list titles / compounds laid out for the old frame. Settings are read back.
- `queue_render` takes `format` / `codec` (unknown values return what is available), `width` / `height`, a `start_seconds`–`end_seconds` range and `export_audio`, reads the job's real settings back from the queue, and returns Resolve to the page it was on (touching render settings switches to Deliver). Verified live on Resolve 20.3 Free: a 9:16 version of a 16:9 edit rendered to a 1080×1920 H.264 MP4 of exactly the requested 3 s, filled edge to edge.
- `grade_clips`: primary colour by numbers (ASC CDL slope / offset / power / saturation on a node) or copy one clip's grade to others. Resolve cannot read a CDL back, so each clip's middle frame is exported before and after and the mean colour change is reported (`visible_change`). Verified live on Resolve 20.3 Free (warm grade, copy, reset).
- `checkpoint`: undo for agents (the scripting API has none). `save` copies the current timeline as "<timeline> · checkpoint <label>" into a Checkpoints bin and keeps you on your timeline (`DuplicateTimeline` makes the copy current, measured on 20.3); `list`; `restore` continues on a fresh copy so checkpoints stay intact; `export_project` writes a .drp backup and checks it on disk. Verified live on Resolve 20.3 Free.
- `add_title`: overlay a Text+ title (text, size, lower-third position, colour, font; read back) at a time and length on a free track above V1, without moving anything. Resolve's own `InsertFusionTitleIntoTimeline` is an insert edit on V1 that splits and ripples the edit (measured on 20.3), so the title is built on a scratch timeline, wrapped as a compound clip (kept in a "Titles" bin for restyling) and appended; longer than one 5 s Text+ is stitched from several. Verified live on Resolve 20.3 Free.
- MCP resources (mcp 1.x and 2.x): `resolve://traps`, `resolve://capabilities` (each tool's channels — studio / bridge / manual / macOS UI — built from the registered tools, plus Free vs Studio, Resolve 21.1+ Free and macOS permission notes), `resolve://state` (`get_resolve_state` without clips when live, otherwise how to connect; bounded to a few seconds) and `resolve://guide/{name}` (also listed per guide).
- Known-traps ledger (`resolve_pilot/traps.py`): each trap with symptom, cause, what resolve-pilot does, the Resolve version it was measured on (or *reported* when only other projects describe it) and the tools affected. Served as `resolve://traps` and `get_workflow_guide("traps")`. `run_lua` results carry `known_traps` for the API methods the code calls (`DeleteClips`, `DuplicateTimeline`, `InsertFusionTitleIntoTimeline`, `SetLUT`, `AppendToTimeline`, `GetItemListInTrack`); bridge timeouts and stale heartbeats say a modal dialog in Resolve may be blocking the scripting API.
- Verified live on Resolve 20.3 Free: `import_media` (bins, reuse), `append_clips` (new timeline at 01:00:00:00, exact source ranges, 23.976 into 24, audio on A2 at a record time; `endFrame` is exclusive), `remove_clips` (ripple), `set_clip_properties` (zoom, pan, opacity, flip, `Scaling` fill via `resolve.SCALE_*`, clip enable, all read back and checked with `timeline_frames`), `set_tracks` (rename, lock, add), `export_timeline` (FCPXML, EDL, OTIO, DRT, AAF, CSV).
- `add_subtitles`: put an SRT (or a transcript, written as SRT first) on the timeline's subtitle track at the file's own times, reusing it from the media pool, refusing to stack on existing captions unless `replace=true`, and reading the captions back. Verified live on Resolve 20.3 Free, timelines starting at 0 and at 01:00:00:00.
- **Seeing footage** — results are images the model looks at, on mcp 1.x and 2.x:
  - `grab_frames`: frames at given times, separately or as one contact sheet (`layout="grid"`).
  - `scene_frames`: one representative frame per detected scene (spread evenly over long videos).

### Fixed
- `timeline_frames` from the Deliver page: Resolve 21.2.0 Free exports no still there ("ExportCurrentFrameAsStill failed" for every position). The stills are now taken on the Edit page and Deliver is opened again afterwards.
- The bridge no longer outlives Resolve. It runs in a process of its own (`fuscript`), and after Resolve quit it kept refreshing its heartbeat with a Resolve object whose methods were all gone: `setup_bridge(status)` said "running", `setup_bridge(start)` answered "already running" and every request failed (seen on 20.3 Free). The bridge now checks every two seconds that Resolve still works and stops with "Resolve quit" once it has worked and no longer does; a bridge started before a project is open keeps waiting, as before.
- Resolve 21.2.0 Free, measured instead of reported: clicking the bridge in Workspace > Scripts starts no script process, and the Console's Lua has lost every way to reach a file, the clipboard or another process (the list is in `resolve://traps`). That is a deliberate removal, and resolve-pilot does not try to get around it. The same measurement shows what still works: a multi-line snippet from this server pasted into the Console runs with the full Resolve API, so the manual channel is intact on 21.2 Free. Status, `setup_bridge`, the trap, the README and the paste instructions say so. `setup_bridge(action="start")` was also run for real here: it started Resolve 21.2 and stopped before the click with that explanation.
- A plan made from phone footage no longer gets the phone's *average* frame rate. A phone records a variable rate, so ffprobe's average for a 24 fps clip is 23.9989 (29.755 for a 30 fps one with dropped frames), and that became the plan's and the FCPXML's rate. Resolve 20.3 imported such a timeline as a 24 fps one with the audio spread over two alternating tracks (99 + 99 of 198 clips) and a one-frame hole after one clip. `probe_media` now reports the file's nominal rate when the average is within 5% of it (what Resolve itself calls the clip), and plans stored with such a rate get a warning that names the rate to set. The same plan at 24: one audio track, 198 of 198 clips on the plan's frames.
- Resolve 21.1.2 Free: the bridge cannot start there (reported in #4: the Console's Lua has no `dofile`, `io` or `ffi`, and the Scripts-menu entry does nothing). On 21.1.2+ Free, `resolve_pilot_status` no longer suggests installing the bridge, and both it and `setup_bridge` say so and point to Resolve 20.3.x Free (`bridge_can_start: false`); 21.1.0-21.1.1 Free keep the console_command note, reported working on 21.1.1. The edition is read from the app bundle, so Studio gets no such note. README, `resolve://capabilities`, the `resolve-21-1-free-lua-sandbox` trap and the verified-live note now say what was reported per patch release instead of "not yet tried".
- `add_title` with a `font` no longer produces a title that fails every render. Text+ kept its default "Semibold" style when only the font changed, and a family without that style cannot be loaded ("Font Not Found: Heiti TC Semibold"). The font and the new `style` parameter are now checked against Fusion's `FontManager` before anything is built: with no style, one the family has is picked (Regular, Medium, …); an unknown family is refused with `similar_fonts`, an unknown style with the family's `styles`. Where Fusion's FontManager cannot be asked, the title is still built and `warnings` says the font and style were not checked. Verified live on Resolve 21.1.1 Free (macOS): Traditional Chinese titles in Heiti TC, with punctuation and line breaks, render correctly. New trap: `textplus-font-keeps-style`.
- macOS UI automation no longer types or clicks into another app: `send_keystroke`, `menu_pick` and the page shortcuts act only after verifying Resolve is frontmost, keystrokes are scoped to Resolve's process, unknown modifier names are rejected (`opt` / `ctl` accepted) and menu labels with quotes are escaped. Dialog-opening AI features report `completed: false` plus the step the user still has to take.
- `probe_media` can no longer hang forever on an unreadable file.

### Tests
- Static check that the bridge and every snippet read no undefined Lua globals (a deleted variable still referenced) and leak none; a stale stop file must not end a freshly started bridge.
- Frames, contact sheets, scene sampling, read_video pairing and quality detectors against real ffmpeg on generated media; marker replacement through the live bridge; images over a real MCP client session.

### Added
- `timeline_frames`: see the edit as Resolve renders it — grades, LUTs, titles, transitions — on any OS. Exports stills of the current timeline at given seconds or frames (drop-frame aware), returns them like `grab_frames` (separate or as a contact sheet), and puts the playhead and page back. Verified live on Resolve 20.3 Free.
- `render_status`: every render job's status, percent and time left, and whether Resolve is rendering; `wait_seconds` polls until it is done.
- `set_clip_properties`: Inspector values (zoom, pan, tilt, rotation, crop, flip, opacity, composite mode, scaling, retime, ...) and clip enable/disable on all or chosen clips of a track. Keys and value types are checked against an allowlist; enum names map to Resolve's own `resolve.*` constants. Every write is read back, and each clip reports `{requested, actual, ok, mismatched}`, so a setter that returns true without applying the value shows up as `ok: false` (`contradicted`). Includes a 9:16 reframe recipe.
- `set_tracks`: add tracks (audio channel layouts too), rename, enable/disable (mute or hide) and lock tracks, each change read back from Resolve.
- `export_timeline`: the current or a named timeline as FCPXML 1.8-1.10, FCP 7 XML, EDL (plain, CDL, SDL, missing clips), AAF (new / existing), OTIO, DRT, CSV / tab text or ALE. `ok` requires a non-empty file (or an FCPXML bundle folder) that Resolve actually wrote; returns its path and size. Defaults to `<timeline>_<date-time>` in resolve-pilot's exports folder.

- **Live timeline building**, without an FCPXML round trip (which always creates a new timeline), through the same Studio API → bridge → paste-Lua routing:
  - `import_media(paths, bin)`: files into the media pool, into a bin (`"B-roll/Day 1"`, created when missing). Files already in that bin are reused, not imported twice. Returns each item's name, `media_pool_id` and `already_in_pool`.
  - `append_clips(clips, timeline | new_timeline, new_timeline_fps)`: source ranges in source seconds (converted with the clip's own fps) onto the current, a named or a new empty timeline (a name clash is refused), on any track (missing tracks are added), video, audio or both, optionally at a record position. Files not in the pool are imported on the fly. Returns the timeline items that landed, with `warnings` where the length, position or track differ from the request.
  - `remove_clips(indices, track, names, ripple)`: destructive; deletes by the indices `get_resolve_state` lists, refusing when the `names` read beforehand no longer match.
  - Based on API behaviour measured with Python on Resolve 21.0.4 Free (plain path strings for ImportMedia, exclusive endFrame, DeleteClips only on the Edit page), then verified from Lua on Resolve 20.3 Free.

- **What has been run in a real Resolve**, per tool: `resolve://capabilities` gives each tool's `verified_live` (Resolve version and edition, OS, channel, what the run covered, or null), and the README's Status section shows the same matrix. Both come from one ledger (`resolve_pilot/verified.py`); a test fails when a tool that needs Resolve is in neither its "run live" nor its "not yet" list, or when the README matrix is out of date.

- The tool list every session loads is about 13% smaller (~2.5k tokens): the input schemas no longer repeat each field name as a generated `title`, and descriptions lose their docstring indentation.

### Hardening (review rounds)
- Bridge: request code that reassigns a global such as `type`, `table` or `os` can no longer break the bridge. Globals a request sets still persist for later requests, but in the bridge's own table, never in Resolve's real globals (which other scripts share).
- Bridge results are capped at about 4 MB (`result_truncated`) besides the 256 KB output cap; output stays a prefix ending in `...<output truncated>`; a value or error whose `__tostring` raises no longer costs the whole result.
- A request that arrives while the bridge is busy (a parallel tool call, or another MCP client) waits up to its timeout for its turn instead of failing at once, then gets its full timeout to run. A busy bridge whose Resolve process died is reported as gone: the heartbeat now ends with the process id (`pid=`), where older readers ignore it. Only an id the server has seen alive counts, so a Resolve whose id cannot be checked from the server (Flatpak, containers) is judged by its heartbeat, even when the server first sees it mid-request. A request running for over 15 minutes is reported as possibly stuck, with how to replace the bridge.
- Windows, non-ASCII user folder: the bridge folder is reached through its 8.3 short name instead of a folder under `C:\Users\Public`, which every account on the machine can write to (and so could have run Lua in your Resolve). Without short names, setup refuses and points at `RESOLVE_PILOT_BRIDGE_DIR`.
- Plans: two MCP servers (Claude Desktop + Claude Code) editing the same plan are serialized with a file lock. Validation checks dissolves, fades and the music bed on exactly the frames the FCPXML exporter writes, so what passes validation is what Resolve imports.
- Exports: `export_fcpxml`, `export_srt` and `export_timeline` never replace an existing file unless `overwrite=true`, and their default names never collide (claimed atomically, or for `export_timeline` stamped uniquely per call), so parallel exports cannot pick the same file. `export_srt` drops zero-length cues and reports how many.
- `detect_beats`: music that is already playing when the file starts no longer counts as a beat at 0:00 or squashes every other beat's strength; a hit right on the first frame is still a beat.

### Resolve 21.1+ Free
- The bridge no longer needs `io`, `os.execute`, `package` or `debug`, which Resolve 21.1+ Free removed from its Lua. When `io` is missing it reads and writes its files through LuaJIT's `ffi` (a global in Resolve), takes the path separator from the MCP server, and the server creates the bridge folder. `rp.file_access` says which one is in use. Tests run the bridge in an emulated 21.1 sandbox. Not yet tried on a real 21.1 install.
- `setup_bridge(install)` returns `console_command`, a one-line `dofile(...)` to paste into the Console when the Scripts menu entry does nothing, and lists older resolve-pilot bridge scripts left in the same menu.
- `resolve_pilot_status` reports `resolve_version` (macOS) and, on 21.1+, how to start the bridge from the Console.

### Permissions (macOS)
- Accessibility and Screen Recording hints now name the app macOS actually checks. Claude Desktop starts MCP servers through a helper that makes the Python interpreter (Python.app) responsible, so "allow Claude" never worked for `screenshot_resolve`.

### Fixed (found in the live run)
- The bridge wrote each reply before clearing its "busy" flag, so a request sent right after the previous one could fail with "Resolve is still running a previous request" (seen as a flaky test in the publish check). The flag is now cleared first, and a request that still finds it set waits for its turn.
- `add_subtitles`: Resolve appends subtitles at the playhead, not at the timeline start, so captions could land seconds late (the read-back warning caught it). The playhead is now parked on the first frame for the append and put back.
- Resolve 20.3 crashes when a subtitle item is appended with a frame range or media type (reproduced twice). `add_subtitles` never does that, `append_clips` refuses subtitle files, and the test mock now fails the same way so a regression cannot reach a user's Resolve.
- Running the test suite replaced the user's installed bridge in Resolve's Scripts menu with one pointing at a pytest folder (a test patched the wrong module), so the menu entry silently did nothing. `RESOLVE_PILOT_SCRIPTS_DIR` / `RESOLVE_PILOT_LUT_DIR` now redirect those folders, and every test sets them, so tests can no longer write into a real Resolve install.
- `run_lua`: request code could not see the `rp` helpers and its `print()` output was lost, because Resolve runs the bridge script in its own environment while `loadstring` compiles against the real globals. Requests now get an environment with both; globals they set still persist between requests. Tests now run the bridge in a separate script environment like Resolve does.
- `analyze_quality` flagged sub-dB wobble on a steady tone as "loud": loud/quiet now also need a 6 dB departure from the local level.
- Runs of the same kind were split when a span of another kind sat between them; merging is now per kind.
- Freeze spans inside black and quiet spans inside silence are dropped (they repeat the stronger finding).
- `add_quality_markers`: spans starting on the same frame become one marker ("Black + Loud") instead of Resolve skipping the second.
- `read_video` on an audio-only file failed with an ffmpeg error per segment; it now returns the speech with a note that there are no frames.

## 0.2.0

Focus: an agent connected to resolve-pilot can now *see* Resolve, act on it, verify the result and iterate — in the Free edition too — while spending fewer tokens.

### Fixed
- **Fresh installs crashed on start.** `mcp>=1.27` now resolves to mcp 2.x, which removed `mcp.server.fastmcp`. The server supports both 1.x and 2.x (`mcp>=1.27,<3`).
- With mcp 2.x, tool errors reached the agent as a bare "Error executing tool X". Every tool now reports what went wrong and what to do next.
- `detect_beats` failed on every file: piped WAV output has no valid size header. Audio is now decoded as raw PCM (and the onset pass is faster).
- `detect_scenes` reported "0 cuts" when ffmpeg could not read the file; it now raises the ffmpeg error.
- Lua snippets embedded paths and names unescaped, so a quote or `]]` broke the Lua (or injected code). All values are now encoded safely, and `~` is expanded before reaching Resolve.
- Transcript rough cuts repeated words: padding made neighbouring clips overlap in the source. Boundaries are now placed between segments.
- FCPXML: clip boundaries are rounded to frames cumulatively (no one-frame gaps or drift over many short cuts); asset URIs are proper `file://` URIs (spaces, `#`, non-ASCII, Windows paths); audio-only assets are declared as such.
- Verified live on Resolve 20.3 (Free, macOS) through the bridge, which turned up:
  - `transition_out_seconds: 0` on a clip was ignored when the plan had a default dissolve, so beat cuts could not be hard cuts. Omitted now means "plan default" and `0` means a hard cut.
  - Timelines read back with transitions counted as clips (`GetItemListInTrack` returns dissolves as items), and `set_clip_color` / `apply_lut` touched them. Transitions are now filtered out, and `get_resolve_state` reports `transition_count`.
  - `apply_lut` applied nothing: Resolve only accepts LUTs inside its LUT folder and returns false for any other path. LUTs are now copied into `<LUT folder>/resolve-pilot/` first and the LUT list is refreshed; if Resolve still rejects every clip the tool returns `ok: false`.
  - Lists from the Resolve API (e.g. `available_presets`) reached the agent as `{"1": ..., "__flags": ...}` objects; the bridge now encodes them as JSON arrays.
  - Plan validation warns when a dissolve leads into a clip without audio: Resolve imports that clip wrapped in a compound clip.

### Added
- **Live Lua bridge** (`resolve_pilot/bridge`): a small Lua loop started from Workspace › Scripts (installed by `setup_bridge`) or pasted into the Console. Request ids, JSON results, captured `print` output, Lua tracebacks, idle timeout, stop command, "newest bridge wins", `rp.*` helpers. Works on macOS, Windows and Linux.

- **Transcripts**: cached per file/model/language, numbered compact segments with paging, background jobs that survive client timeouts, `plan_from_transcript(transcript_id, segment_indices=[…])`, and a faster-whisper engine for Windows / Linux / Intel Macs (`.[transcribe-cpu]`).
